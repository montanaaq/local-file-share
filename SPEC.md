# ТЗ: Local File Share. Прямая передача файлов и текста по собственному UDP-протоколу

## 1. Контекст

Семестровая работа по сетевому программированию. Цель: спроектировать и реализовать собственный прикладной протокол поверх UDP для обнаружения устройств, передачи файлов и текста, подтверждений, паузы и возобновления.

Приложения обмениваются пакетами напрямую, peer-to-peer, в одной локальной сети. Отдельного сервера и регистрации нет. Каждое приложение одновременно отправляет и принимает данные, самостоятельно хранит список известных устройств и состояние своих передач. Файлы любого типа передаются как байты.

Передача переживает временный обрыв связи. Клиент хранит fileId, принятые чанки и индекс первого недостающего чанка в памяти, а данные в `.part`. После восстановления доступности устройства передача продолжается с места обрыва.

Оценивают формат пакетов, таблицу сообщений, подтверждения, поиск устройств, паузу и возобновление, UI и демонстрацию. Установки транспортного соединения, скользящего окна и контроля перегрузки нет.

## 2. Стек и ограничения

- .NET 10, `net10.0`, C#, nullable enabled, async/await для сетевых операций.
- Целевая структура решения: `Protocol` как общая библиотека и `Client` как Avalonia-приложение с ProjectReference на Protocol, а также `tests/Protocol.Tests` с xUnit. Проект Server больше не нужен. Его удаление из решения выполняется отдельным шагом, изменение ТЗ само по себе не удаляет код.
- Использовать существующий клиент в `src/Client`: Avalonia 12.1.3, Avalonia.Desktop, Themes.Fluent, Fonts.Inter, CommunityToolkit.Mvvm 8.4.2.
- Сеть только через `System.Net.Sockets.UdpClient`, с `EnableBroadcast` для поиска устройств. Для CRC32 использовать установленный System.IO.Hashing. Не добавлять зависимости без необходимости.
- Целевые ОС: Windows, macOS, Linux. Разработка на macOS.
- До использования незнакомого API сверяться с официальной документацией установленной версии. Для Avalonia 12 проверять drag & drop, StorageProvider и Clipboard.
- Сохранять существующие имена и структуру файлов. Простой код без DI-контейнеров, интерфейсов на будущее и лишних слоёв. Идентификаторы на английском, комментарии только для неочевидных причин.
- Вне объёма: TCP поверх UDP, скользящее окно, шифрование и аутентификация, NAT traversal, обмен через интернет, мобильные ОС, передача папок, обнаружение за пределами одной подсети, возобновление после перезапуска приложения. deviceId идентифицирует экземпляр приложения, но не подтверждает его подлинность.

## 3. Формат пакета

Заголовок 12 байт: version 1 байт, type 1 байт, seq uint32, payloadLength uint16, crc32 uint32. Далее payload. Порядок числовых полей big-endian, использовать BinaryPrimitives. Версия протокола 1. CRC32 считается по заголовку с обнулённым полем CRC и payload.

- Новый пакет получает новый seq, включая сообщения без ACK. Повторы одной reliable-отправки сохраняют seq. Счётчик общий для отправителя, не отдельный для каждого получателя.
- Все Guid передаются как 16 байт в big-endian представлении. Для записи и чтения использовать согласованные перегрузки Guid с явным порядком байт.
- Размер данных чанка до 1024 байт. Максимальный payload 1060 байт, максимальная датаграмма протокола 1072 байта. Это полный CHUNK с заголовком и идентификаторами.
- Пакеты с неверной версией, CRC, неизвестным типом, несовпадением длины или превышением лимита молча отбрасываются. Некорректный payload не подтверждается и не выполняется.

## 4. Сообщения

D = deviceId отправителя, Guid 16 байт. Это первое поле каждого payload. Приложение создаёт случайный deviceId при запуске и сохраняет до закрытия. Получатель задаётся endpoint назначения, IP и UDP-портом. Серверных peerId и подмены payload нет.

Имя кодируется как длина 1 байт и UTF-8, максимум 255 байт. Пустое имя и некорректный UTF-8 не допускаются. Размеры ниже относятся к payload.

| Код | Сообщение | Направление | Payload | ACK |
|---|---|---|---|---|
| 0x02 | HEARTBEAT | приложение → известное устройство | D | да, без повторов HEARTBEAT |
| 0x03 | ACK | получатель → отправитель | D, ackedSeq uint32 | нет |
| 0x05 | DISCOVER | приложение → broadcast или заданный endpoint | D, имя устройства | нет |
| 0x06 | PEER_INFO | приложение → источник DISCOVER | D, имя устройства | нет |
| 0x20 | FILE_OFFER | отправитель → получатель | D, fileId Guid 16, size uint64, sha256 32 байта, имя файла | да |
| 0x21 | FILE_ANSWER | получатель → отправитель | D, fileId, accepted 1 байт, nextIndex uint32 | да |
| 0x30 | CHUNK | отправитель → получатель | D, fileId, index uint32, данные до 1024 байт | да |
| 0x31 | FILE_DONE | отправитель → получатель | D, fileId | да |
| 0x32 | FILE_RESULT | получатель → отправитель | D, fileId, ok 1 байт | да |
| 0x40 | CLIPBOARD | отправитель → получатель | D, текст UTF-8 до 1000 байт | да |

- HELLO, ERROR, SERVER_INFO и PEER_LIST удалены из протокола. Коды 0x01, 0x04 и 0x10 не используются. ACK больше не содержит assignedId.
- DISCOVER и PEER_INFO сообщают имя и идентификатор, адрес и порт берутся из источника датаграммы. DISCOVER позволяет обеим сторонам узнать друг друга без регистрации.
- accepted и ok принимают только 0 или 1. nextIndex означает первый недостающий чанк, для нового файла равен 0, при accepted = 0 игнорируется.
- FILE_OFFER с известным fileId от того же deviceId запрашивает возобновление. Имя, размер и SHA-256 должны совпадать с исходным предложением. Изменённые метаданные отклоняются через FILE_ANSWER с accepted = 0.
- Все поля фиксированной длины проверяются до чтения. Для payload с именем длина должна точно соответствовать указанному числу байт, лишние байты не допускаются.

## 5. Поиск устройств и доступность

- Каждое приложение слушает UDP-порт 5000 по умолчанию на локальных интерфейсах. Локальный порт настраивается до запуска обмена. При занятом порте показать ошибку и предложить другой порт, не включать совместное использование порта для обхода конфликта.
- Пока сетевой обмен включён, приложение раз в DiscoverInterval 2 с отправляет DISCOVER на 255.255.255.255:5000 и 127.0.0.1:5000. Получатель отвечает PEER_INFO на endpoint источника. Своё deviceId игнорируется. Повторов reliable для поиска нет, потерянный запрос заменяется следующим.
- Список строится локально по deviceId. Новый DISCOVER или PEER_INFO добавляет устройство либо обновляет имя и endpoint существующего устройства. После смены IP тот же deviceId позволяет связать устройство с незавершённой передачей.
- Для устройств на нестандартном порте и при блокировке broadcast есть ручной ввод IP:порт. На этот endpoint также отправляется DISCOVER раз в 2 с. Вручную добавленные адреса хранятся до закрытия приложения.
- HEARTBEAT раз в 1 с посылается известным устройствам онлайн и устройствам с передачами в паузе. Получатель отвечает ACK, сам HEARTBEAT не повторяется. ACK сверяется по deviceId, endpoint и ackedSeq. Только корректные сообщения от ожидаемого устройства обновляют время его доступности.
- Если от устройства 3 с нет сообщений, показывать отсутствие связи с ним. После PeerTimeout 5 с без сообщений убрать его из списка онлайн. Запись известного устройства и состояние передачи сохраняются в памяти до закрытия приложения, для передачи действует PauseTimeout.
- Повторное обнаружение того же deviceId обновляет endpoint и возвращает устройство в список онлайн. Нажимать кнопку подключения заново не нужно. Возобновление выполняет отправитель по правилам раздела 6.
- Broadcast ограничен одной подсетью. Ручной адрес помогает при блокировке broadcast, но не обходит запрет прямого обмена между устройствами. Для работы необходима доступность входящего UDP-порта на каждом устройстве.
- Для двух экземпляров на одном компьютере использовать разные порты, например 5000 и 5001. Экземпляр на 5001 обнаруживает первый через 127.0.0.1:5000, а первый узнаёт его endpoint из DISCOVER. Ручной адрес 127.0.0.1:5001 также допустим.

## 6. Надёжность и передача

- Все сообщения и ACK идут напрямую между приложениями. Надёжность реализуется на концах обмена.
- Reliable-отправка ждёт ACK 200 мс, всего не более 5 отправок с одним seq. Подтверждение должно относиться к нужному deviceId, endpoint и seq. Для CHUNK и FILE_DONE исчерпание попыток означает паузу, для остальных reliable-сообщений ошибку, кроме FILE_OFFER для возобновления. Приложение обрабатывает недоступность адресата по тайм-аутам, серверных ERROR нет.
- Один цикл читает UDP-сокет и распределяет входящие сообщения. Ожидание ACK не должно поглощать обычные сообщения или подтверждения других отправок.
- На дубликат reliable-сообщения повторно отвечать ACK, действие повторно не выполнять. Для CHUNK запись по смещению index * 1024 идемпотентна; остальные сообщения используют ограниченный набор последних пар deviceId и seq. Повторный FILE_DONE для завершённой передачи дополнительно вызывает повтор FILE_RESULT.
- Сценарий файла: FILE_OFFER, FILE_ANSWER, CHUNK по одному с stop-and-wait, FILE_DONE, FILE_RESULT. ACK подтверждает обработку сообщения, FILE_ANSWER сообщает решение пользователя, FILE_RESULT сообщает результат проверки файла.
- Лимит файла 20 * 1024 * 1024 байт. Получатель пишет в `.part`, ведёт список принятых чанков и nextIndex. Проверяет индекс, длину чанка и соответствие размеру файла. Пустой файл имеет 0 чанков, после принятия сразу следует FILE_DONE.
- После FILE_DONE проверить наличие всех чанков и SHA-256. При успехе переименовать `.part` и послать FILE_RESULT с ok = 1. При неуспехе удалить `.part` и послать ok = 0. Очищать имя файла, учитывать запрещённые имена и символы Windows и коллизии. Папка по умолчанию "Загрузки", при совпадении имени добавлять суффикс вроде (1).
- Тайм-аут FILE_ANSWER 60 с завершает передачу ошибкой. Тайм-аут FILE_RESULT 30 с переводит отправителя в паузу. Во время приёма отсутствие чанков 10 с переводит получателя в паузу; этот таймер не действует во время решения пользователя и проверки SHA-256.
- LossRate от 0 до 100% случайно отбрасывает пакеты при отправке и приёме каждого приложения, включая обнаружение и ACK. Значение 100 имитирует полный обрыв. Временный консольный клиент поддерживает --loss N и команду loss N, Avalonia-клиент содержит поле LossRate и переключатель обрыва связи.
- Общие настройки собирать в ProtocolConstants: порт 5000, чанк 1024, лимиты файла и текста, ACK 200 мс, 5 отправок, HEARTBEAT 1 с, потеря связи 3 с, PeerTimeout 5 с, DiscoverInterval 2 с, FILE_ANSWER 60 с, FILE_RESULT 30 с, отсутствие чанков 10 с, PauseTimeout 120 с, ProbeInterval 2 с. Размеры и смещения полей хранить в существующих PacketOffsets, PayloadsConstants и Packet, не дублировать.

### Пауза и возобновление

- Состояния передачи: ожидание ответа, передача, пауза, проверка, готово, отклонено, ошибка, отменено.
- Отправитель уходит в паузу после неподтверждённого CHUNK или FILE_DONE либо тайм-аута FILE_RESULT. Получатель уходит в паузу после 10 с без чанков. `.part`, принятые чанки и nextIndex сохраняются.
- В паузе отправитель раз в ProbeInterval повторяет FILE_OFFER с тем же fileId и новым seq на текущий endpoint устройства. Неудача запроса сохраняет паузу. Отсутствие ответа не прекращает поиск устройства.
- Получатель с незавершённой передачей от этого deviceId отвечает FILE_ANSWER с accepted = 1 и своим nextIndex без нового запроса пользователю. Неизвестный fileId считается новым предложением.
- Отправитель продолжает с nextIndex получателя, даже если его счётчик подтверждённых чанков отличается. nextIndex не должен превышать число чанков. Если он равен числу чанков, сразу отправить FILE_DONE.
- Для успешно завершённой передачи повторный FILE_OFFER получает FILE_ANSWER с accepted = 1 и nextIndex равным числу чанков. Следующий FILE_DONE получает ACK и сохранённый FILE_RESULT. Для завершённой проверки с ok = 0 повторный FILE_OFFER получает FILE_ANSWER с accepted = 0. Результаты хранятся по deviceId отправителя и fileId до закрытия приложения.
- Каждая сторона отсчитывает PauseTimeout от собственного входа в паузу. Без успешного возобновления пауза дольше 120 с завершается ошибкой; получатель удаляет `.part`. Пробные запросы сами по себе не сбрасывают таймер паузы.
- Пользователь может отменить передачу в паузе. Получатель при локальной отмене удаляет `.part`. Сообщения отмены нет, вторая сторона завершает передачу по своему PauseTimeout.

## 7. Клиент

Одно окно Avalonia, MVVM на CommunityToolkit.Mvvm.

- Сверху имя устройства, локальный порт и переключатель сетевого обмена. По умолчанию обмен включён. Отключение останавливает обнаружение и сетевые операции, незавершённые передачи переходят в паузу, таймер паузы продолжает действовать.
- Слева список устройств онлайн с именем, адресом и состоянием доступности. Выбранное устройство является получателем. Под списком ручное добавление IP:порт. Подключения к серверу нет.
- По центру зона drag & drop, кнопка выбора файла и кнопка отправки текста из буфера обмена.
- Входящее предложение содержит имя, размер и кнопки принятия и отклонения. Папка сохранения по умолчанию "Загрузки".
- Снизу список передач с направлением, именем, прогрессом, статусом и счётчиком повторов. В паузе прогресс сохраняется, показано время до ошибки и кнопка отмены.
- Панель "Подробности" содержит отправки, подтверждения, повторы, потери, паузы, возобновления и поле LossRate. Переключатель "Обрыв связи" устанавливает LossRate 100 и возвращает прежнее значение при выключении. Сетка состояний чанков необязательна.
- Принятый текст показывается карточкой с кнопкой копирования.

## 8. Порядок работы

Выполнять только запрошенный этап. После каждого этапа давать команды запуска и небольшую проверку поведения.

1. Protocol: актуальные типы и payload P2P, сериализация, CRC32, единый приём, SendReliableAsync, ACK и LossRate. Перевести существующий формат с peerId на deviceId и добавить тесты.
2. Удаление проекта Server из решения и обновление ссылок и документации отдельным запросом. Проверить сборку двух основных проектов и тестов.
3. Прямой обмен через временный консольный клиент: DISCOVER, PEER_INFO, список устройств, HEARTBEAT, отправка файла и проверка SHA-256. Тестировать двумя экземплярами с разными портами.
4. Пауза и возобновление, обнаружение вернувшегося устройства и обновление endpoint. Проверка: loss 100 на одном из экземпляров, через 15 с loss 0.
5. CLIPBOARD.
6. Avalonia UI с поиском устройств, ручным адресом и прямой передачей.
7. Статистика, README и PROTOCOL.md.

## 9. Результат и демо

- Исходный код и LocalFileShare.slnx, README с командами сборки и запуска приложений, портами и условиями прямого UDP-обмена.
- PROTOCOL.md примерно на одну страницу: заголовок, таблица сообщений, поиск устройств, ACK, тайм-ауты, передача и возобновление.
- Два экземпляра на одном компьютере с портами 5000 и 5001 видят друг друга и передают файл около 5 МБ; SHA-256 совпадает, файл открывается.
- При LossRate от 20 до 30% файл доходит целым, счётчик повторов больше нуля. Отклонение файла завершает передачу у отправителя.
- Обрыв на время от 10 до 20 с во время передачи вызывает паузу. После восстановления связи передача продолжается с первого недостающего чанка, SHA-256 совпадает. Проверить обрыв у отправителя и получателя.
- Обрыв дольше PauseTimeout завершает передачу ошибкой, бесконечного ожидания нет. Получатель очищает `.part`, если приложение продолжает работать.
- Текст приходит напрямую и копируется на втором устройстве.
- macOS и Windows в одной сети с портом 5000 обнаруживают друг друга без ручного адреса. После закрытия одного приложения оно исчезает из списка другого не позже PeerTimeout 5 с. Выключение Wi-Fi на время от 10 до 20 с во время передачи вызывает паузу и последующее возобновление без перезапуска приложений.
