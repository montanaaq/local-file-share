# ТЗ: Local File Share — передача файлов и текста между устройствами по собственному UDP-протоколу

## 1. Контекст
Семестровая работа по сетевому программированию. Цель: спроектировать и реализовать собственный прикладной протокол поверх UDP. Надёжность по UDP тут вторична, это не проект «TCP поверх UDP». Оценивают протокол (формат пакетов, таблица сообщений, подтверждения), UI и наглядность демонстрации. Идея согласована с преподавателем.

Суть: аналог AirDrop для своих устройств. Сервер в центре, клиенты на разных устройствах видят друг друга в списке и отправляют файлы любого типа (фото, видео, документы, контакты .vcf; для протокола это просто байты) и текст из буфера обмена. Все пакеты между клиентами идут через сервер (relay). Работает в локальной сети, адрес сервера вводится в клиенте.

## 2. Стек и ограничения
- .NET 10 (net10.0), C#, Nullable enabled, async/await.
- Три проекта в одном решении: `Protocol` (class library), `Server` (консоль), `Client` (Avalonia UI). Клиент уже создан в папке `local-file-share`: Avalonia 12.1.3, Avalonia.Desktop, Themes.Fluent, Fonts.Inter, CommunityToolkit.Mvvm 8.4.2. Использовать его, добавить ProjectReference на `Protocol`.
- Сеть: только `System.Net.Sockets.UdpClient`. Контрольная сумма: CRC32 (`System.IO.Hashing` или своя простая реализация). Других внешних зависимостей нет.
- Целевые ОС клиента: Windows, macOS, Linux. Автор разрабатывает на macOS.
- Avalonia 12: использовать актуальное API версии 12, а не 11. Drag & drop, StorageProvider (выбор файла), Clipboard могли измениться, сверяйся с документацией.
- Стиль кода: чистый и простой, без over-engineering. Без DI-контейнеров, интерфейсов «на будущее» и лишних слоёв. Короткие методы, говорящие имена, комментарии только там, где неочевидно «почему». Идентификаторы на английском. Никакого шаблонного «нейрослопа»: болтливых комментариев, дублирования, ненужных обёрток.
- Вне объёма: скользящее окно, шифрование, P2P/NAT, мобильные ОС, передача папок.

## 3. Формат пакета (порядок байт big-endian, `BinaryPrimitives`)
Заголовок 12 байт: version (1, =1) | type (1) | seq (uint32) | payloadLength (uint16) | crc32 (uint32; считается по заголовку с обнулённым полем crc и по payload). Далее payload. Пакет с неверным CRC или версией молча отбрасывается.
- seq: счётчик отправителя, +1 на каждый отправленный пакет (в том числе без ACK).
- Размер чанка файла 1024 байта, максимальный пакет около 1060 байт (без фрагментации IP).

## 4. Сообщения
P = peerId (uint16): у сообщений между клиентами это первое поле payload. Клиент указывает получателя, сервер при пересылке подменяет P на id отправителя. Сервер имеет id 0.

| Код | Сообщение | Направление | Payload | ACK |
|---|---|---|---|---|
| 0x01 | HELLO | клиент → сервер | имя устройства (длина 1 байт + UTF-8) | да |
| 0x02 | HEARTBEAT | клиент → сервер | — | нет |
| 0x03 | ACK | любой → любой | P, ackedSeq (uint32); в ответе на HELLO ещё assignedId (uint16) | нет |
| 0x04 | ERROR | сервер → клиент | code (1), seq упавшего пакета (uint32) | нет |
| 0x10 | PEER_LIST | сервер → клиент | count (uint16), далее count × (id uint16, имя); все онлайн-устройства, кроме адресата | да |
| 0x20 | FILE_OFFER | отправитель → получатель | P, fileId (Guid 16), size (uint64), sha256 (32), имя файла (длина 1 + UTF-8) | да |
| 0x21 | FILE_ANSWER | получатель → отправитель | P, fileId, accepted (1) | да |
| 0x30 | CHUNK | отправитель → получатель | P, fileId, index (uint32), данные (до 1024) | да |
| 0x31 | FILE_DONE | отправитель → получатель | P, fileId | да |
| 0x32 | FILE_RESULT | получатель → отправитель | P, fileId, ok (1) | да |
| 0x40 | CLIPBOARD | отправитель → получатель | P, текст UTF-8 (до 1000 байт) | да |

Коды ERROR: 1 — получатель не найден или офлайн, 2 — клиент не зарегистрирован (не было HELLO).

## 5. Правила протокола
- ACK end-to-end: подтверждает тот, кому адресовано сообщение; сервер лишь пересылает (включая ACK). Только HELLO и PEER_LIST подтверждаются между клиентом и сервером напрямую.
- Reliable-отправка: послать, ждать ACK с нужным seq 200 мс, до 5 отправок, затем ошибка передачи. Получив ERROR на свой seq, отправитель сразу прекращает повторы.
- Дубликаты: получатель повторно отвечает ACK, но действие не выполняет. Для CHUNK это запись по смещению `index * 1024` (идемпотентна), для остальных сообщений ограниченный набор последних (peerId, seq).
- Передача файла: FILE_OFFER → FILE_ANSWER → чанки по одному (stop-and-wait) → FILE_DONE → FILE_RESULT. Получатель пишет в `.part`-файл, после FILE_DONE проверяет, что получены все чанки, считает SHA-256 и отвечает FILE_RESULT; при успехе переименовывает файл. Тайм-ауты: ожидание FILE_ANSWER 60 с, FILE_RESULT 30 с, получатель отменяет приём, если 10 с нет чанков.
- HEARTBEAT раз в 1 с; сервер удаляет устройство после 5 с тишины и рассылает обновлённый PEER_LIST (также при подключении).
- Сервер без состояния передач: он ведёт только реестр устройств (id, имя, endpoint, время последнего пакета) и пересылает пакеты.
- Симуляция потерь: общий для сервера и клиента параметр `LossRate` (0–100%), пакеты случайно отбрасываются при приёме и при отправке. На сервере задаётся аргументом `--loss N` и консольной командой `loss N`. Нужна для демонстрации.
- Константы (порт сервера по умолчанию 5000, размер чанка, таймауты, лимит размера файла 20 МБ) вынесены в одно место и настраиваются.

## 6. Клиент (Avalonia, MVVM на CommunityToolkit.Mvvm)
Одно окно, без перегруженности:
- Сверху: поля «IP сервера», порт, имя устройства, кнопка подключения (локальный порт клиента по умолчанию выбирает ОС, чтобы можно было запустить несколько клиентов на одном компьютере).
- Слева: список устройств онлайн (выбранное устройство получатель).
- По центру: зона drag & drop и кнопка «Выбрать файл», кнопка «Отправить текст из буфера обмена».
- Входящее предложение файла: карточка с именем, размером и кнопками «Принять» / «Отклонить». Папка сохранения по умолчанию «Загрузки»; имя файла очищается от запрещённых символов (в т. ч. для Windows), при совпадении добавляется суффикс (1).
- Снизу: список передач (направление, имя, прогресс-бар, статус: ожидание ответа / передача / проверка / готово / отклонено / ошибка) и счётчик повторных отправок.
- Сворачиваемая панель «Подробности»: статистика протокола (отправлено, подтверждено, повторов, потерь). По желанию: сетка чанков с цветом по состоянию (отправлен, подтверждён, повторён).
- Принятый текст из буфера обмена показывается карточкой с кнопкой «Копировать».

## 7. Порядок работы (каждый этап собирается и запускается)
1. `Protocol`: заголовок, сериализация и разбор, CRC32, транспорт с `SendReliableAsync`, ACK и `LossRate`.
2. `Server`: HELLO, HEARTBEAT, PEER_LIST, relay, ERROR, консольные логи.
3. Передача файлов через временный консольный клиент, проверка SHA-256.
4. CLIPBOARD.
5. Avalonia-клиент.
6. Статистика, панель подробностей, README и PROTOCOL.md.
После каждого этапа дай команды запуска и способ проверки.

## 9. Критерии приёмки (демо)
1. Сервер и два клиента на одном компьютере: файл около 5 МБ передаётся, SHA-256 совпадает, файл открывается.
2. Потери 20–30%: файл всё равно доходит целым, счётчик повторов больше нуля.
3. Отклонение файла получателем корректно завершает передачу.
4. Отключение получателя во время передачи даёт у отправителя статус «ошибка», а не бесконечное ожидание.
5. Текст из буфера обмена доходит и копируется на втором клиенте.
6. Два компьютера (macOS и Windows) в одной сети, IP сервера задан в клиенте.
