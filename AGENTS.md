# Инструкции для нейросети

## Как помогать

Это учебная семестровая работа по сетевому программированию. Автор хочет написать реализацию сам. Полное ТЗ находится в [SPEC.md](SPEC.md).

- Выполняй только конкретно запрошенный шаг. Наличие полного ТЗ не разрешает реализовать весь проект.
- По умолчанию объясняй подход, предлагай следующий небольшой шаг и помогай разобраться с ошибками. Пиши готовую реализацию только по запросу автора.
- Если просят структуру, ограничься проектами, ссылками между ними и кратким описанием ответственности. Не добавляй заранее сервисы, интерфейсы, заглушки методов и готовую бизнес-логику.
- Общайся на русском. Идентификаторы в коде пиши на английском.
- Перед изменениями изучай существующий код и используй принятые в проекте подходы.
- Перед архитектурным изменением коротко объясняй его пользу и компромисс.
- Не переписывай самостоятельную работу автора без необходимости для текущего запроса.

## Стек и структура

- .NET 10, `net10.0`, C#, nullable enabled, `async/await` для сетевых операций.
- `LocalFileShare.slnx` объединяет три проекта в `src/` и тестовый проект в `tests/`.
- `src/Protocol/Protocol.csproj` содержит общие типы и форматы протокола. Не зависит от Client и Server. Все существующие типы библиотеки используют namespace `Protocol`.
- `src/Protocol/Packet/` содержит `Packet` с сериализацией, разбором и CRC32, а также `PacketOffsets` со смещениями полей заголовка.
- `src/Protocol/Payloads/` содержит `Payloads` с кодированием и декодированием CHUNK и FILE_OFFER, а также `PayloadsConstants` с размерами и смещениями полей. Используй эти типы для дальнейших форматов payload.
- `MessageType` и `ErrorCode` уже определены. `ProtocolConstants` и `UdpTransports` пока пустые. Не считай UDP-транспорт реализованным и не создавай параллельные типы без необходимости.
- `src/Server/Server.csproj` ссылается на Protocol. Пока `Program.cs` проверяет сериализацию и CRC32 пакета; relay-сервер ещё не реализован.
- `src/Client/Client.csproj` является Avalonia-клиентом и ссылается на Protocol. Сохраняй папки `Views/`, `ViewModels/`, `Models/` и `Assets/` внутри проекта.
- Namespace клиента сейчас различаются: `Client` у Program, App и ViewLocator, `ViewModels` у моделей представления, `local_file_share.Views` у MainWindow. Учитывай существующие объявления и ссылки в XAML; не переименовывай их вне текущего запроса.
- В `Client.csproj` осталось `DefaultItemExcludes` для `Protocol/**` и `Server/**`. После переноса проектов это старое исключение, а не основа структуры решения. Не возвращай проекты в корень ради него.
- `tests/Protocol.Tests/Protocol.Tests.csproj` ссылается на Protocol и использует xUnit. `PacketTests` проверяет сериализацию и разбор; `PayloadsTests` пока содержит пустой тест и не проверяет payload.
- Клиент использует Avalonia 12.1.3 и CommunityToolkit.Mvvm 8.4.2. Целевые ОС: Windows, macOS, Linux.
- Сеть только через `System.Net.Sockets.UdpClient`. Для CRC32 уже используется `System.IO.Hashing` 10.0.12.
- Не добавляй новые зависимости без необходимости. Не вводи DI-контейнеры, интерфейсы на будущее и лишние слои.
- До использования незнакомого API сверяйся с официальной документацией для установленной версии. Особенно проверяй Avalonia 12: drag & drop, StorageProvider и Clipboard. Не переноси API из Avalonia 11 наугад.
- Следуй локальным инструкциям RTK из `/Users/amir/.codex/RTK.md`, если файл доступен. Команды оболочки запускай через `rtk`; для неподдерживаемых команд используй `rtk proxy`.

## Требования, которые нужно сохранять при реализации

- Все сообщения между клиентами проходят через сервер. Сервер хранит только реестр устройств, без состояния передач.
- Заголовок 12 байт: version 1 байт, type 1 байт, seq uint32, payloadLength uint16, crc32 uint32. Порядок байт big-endian, использовать `BinaryPrimitives`.
- Версия протокола 1. CRC32 считается по заголовку с обнулённым полем CRC и payload. Пакеты с неверной версией или CRC молча отбрасываются.
- `seq` увеличивается на каждый новый пакет отправителя, включая сообщения без ACK. Повторы одной reliable-отправки должны сохранять seq, чтобы ACK и защита от дубликатов работали.
- Коды сообщений и payload брать из таблицы в SPEC.md, не придумывать другой формат. Для клиентских сообщений первое поле payload `peerId` uint16. Сервер подменяет id получателя на id отправителя; id сервера 0.
- ACK end-to-end, сервер пересылает также ACK. HELLO и PEER_LIST подтверждаются непосредственно между клиентом и сервером.
- Reliable-отправка ждёт ACK 200 мс, всего не более 5 отправок. ERROR на свой seq сразу прекращает повторы. ACK, HEARTBEAT и ERROR не требуют ACK.
- На дубликат снова отвечать ACK, действие повторно не выполнять. Для CHUNK писать по смещению `index * 1024`; для остальных сообщений хранить ограниченный набор последних `(peerId, seq)`.
- Сценарий файла: FILE_OFFER, FILE_ANSWER, CHUNK по одному с stop-and-wait, FILE_DONE, FILE_RESULT. Размер чанка 1024 байта, лимит файла 20 МБ, текст UTF-8 до 1000 байт.
- Принимать файл в `.part`, проверять наличие всех чанков и SHA-256 перед переименованием. Очищать имя файла, учитывать Windows и коллизии имён. Папка по умолчанию "Загрузки".
- Тайм-аут FILE_ANSWER 60 с, FILE_RESULT 30 с, отсутствие входящих чанков 10 с отменяет приём.
- HEARTBEAT раз в 1 с. Сервер удаляет устройство после 5 с тишины и обновляет PEER_LIST при подключении и отключении.
- Порт по умолчанию 5000, локальный порт клиента выбирает ОС. Общие настройки протокола собирать в `ProtocolConstants` по мере реализации. Смещения и размеры полей уже находятся в `PacketOffsets`, `PayloadsConstants` и `Packet`; не дублируй их.
- LossRate 0–100% моделирует потери на приёме и отправке в сервере и клиенте. Сервер поддерживает `--loss N` и консольную команду `loss N`.
- UI: подключение, список устройств, выбор файла и drag & drop, отправка текста, принятие/отклонение файла, список передач с прогрессом и статусом, счётчик повторов, панель статистики, карточка принятого текста с копированием.
- Вне объёма: TCP поверх UDP, скользящее окно, шифрование, P2P/NAT, мобильные ОС, передача папок.

## Порядок и проверка

Иди по этапам из SPEC.md только в пределах текущего запроса: Protocol, Server, файл через временный консольный клиент, CLIPBOARD, Avalonia UI, статистика и документация. Временный клиент добавлять только на этапе проверки файлов.

- После запрошенного изменения проверяй сборку через `rtk proxy dotnet build LocalFileShare.slnx`. Не скрывай ошибки и не подавляй предупреждения вместо исправления причины.
- После изменения логики Protocol запускай `rtk proxy dotnet test tests/Protocol.Tests/Protocol.Tests.csproj`. Дополняй существующие тесты проверками поведения в пределах запроса; пустой тест не подтверждает работоспособность.
- Команды запуска текущих проектов: `rtk proxy dotnet run --project src/Server/Server.csproj` и `rtk proxy dotnet run --project src/Client/Client.csproj`.
- Для реализованной логики предлагай небольшую проверку поведения. После этапа указывай команды запуска и способ проверки, отличай проверенные сценарии от ещё не проверенных.
- Для итогового демо нужны два клиента, файл около 5 МБ с совпадающим SHA-256, потери 20–30% с повторами, отклонение файла, ошибка при отключении получателя, текст с копированием и обмен между macOS и Windows в одной сети.
