# Инструкции для нейросети

## Как помогать

Это учебная семестровая работа по сетевому программированию. Автор хочет написать реализацию сам. Полное ТЗ находится в [SPEC.md](SPEC.md).

- Выполняй только конкретно запрошенный шаг. Наличие полного ТЗ не разрешает реализовать весь проект.
- По умолчанию объясняй подход, предлагай следующий небольшой шаг и помогай разобраться с ошибками. Пиши готовую реализацию только по запросу автора.
- Если просят структуру, ограничься проектами, ссылками между ними и кратким описанием ответственности. Не добавляй заранее сервисы, интерфейсы, заглушки методов и готовую бизнес-логику.
- Документацию, Markdown-файлы и итоговые отчёты (summary) пиши на русском. Код, комментарии, сообщения приложения и тексты коммитов пиши на английском.
- Перед изменениями изучай существующий код и используй принятые в проекте подходы.
- Перед архитектурным изменением коротко объясняй его пользу и компромисс.
- Не переписывай самостоятельную работу автора без необходимости для текущего запроса.
- Если описание требований здесь расходится с SPEC.md, следуй актуальному SPEC.md. Не дополняй неоднозначные правила новыми форматами или поведением без обсуждения с автором.

## Конвенции кода

- Форматирование C# — CSharpier; кодировка, отступы и окончания строк — из `.editorconfig`.
- Код, идентификаторы, комментарии в коде, все сообщения приложения и тексты коммитов — английские. Русский использовать только для документации, Markdown-файлов и итоговых отчётов (summary). Имена сообщений протокола и команд не переводить.
- Типы и методы — PascalCase, параметры и локальные переменные — camelCase, закрытые поля — `_camelCase`, константы — PascalCase. Пространства имён — файловые.
- У условий и циклов всегда ставить фигурные скобки. `var` использовать, когда тип очевиден или его имя не помогает чтению; для простых числовых и строковых значений указывать тип.
- Аргументы проверять через явный `if` и `throw`: `ArgumentNullException` для `null`, `ArgumentOutOfRangeException` для диапазона, `ArgumentException` для других неверных аргументов. Указывать `nameof` параметра и английское сообщение. Неверное состояние — `InvalidOperationException`, освобождённый объект — `ObjectDisposedException`.
- Отмена — через `CancellationToken.ThrowIfCancellationRequested()`. Ожидаемую отмену перехватывать с проверкой токена. Сохранять исходное исключение через `throw;`, не скрывать неожиданные ошибки.
- Ресурсы освобождать через `using` / `await using`, захват `SemaphoreSlim` — через `try/finally`. Короткое синхронное изменение состояния защищать `lock`; не заменять все блокировки семафорами.
- Папки группировать по задаче (`Peers`, `Transfers`, `Transport`), интерфейс хранить рядом с реализацией. Добавлять интерфейс только для используемого контракта или подмены в тестах.
- README.md содержит только структуру проекта. Требования — в SPEC.md, сетевой формат — в PROTOCOL.md.

## Стек и структура

- .NET 10, `net10.0`, C#, nullable enabled, `async/await` для сетевых операций.
- LocalFileShare.slnx содержит Protocol и Client в `src/` и Protocol.Tests в `tests/`. Проект Server удалён, отдельного сервера в P2P нет.
- `src/Protocol/Protocol.csproj` содержит общие типы и форматы протокола. Не зависит от Client. Все существующие типы библиотеки используют namespace `Protocol`.
- `src/Protocol/Packet/` содержит `Packet` с сериализацией, разбором и CRC32, а также `PacketOffsets` со смещениями полей заголовка.
- `src/Protocol/Payloads/` содержит кодирование, декодирование и проверку всех payload из SPEC.md, а также PayloadsConstants со смещениями. Форматы используют deviceId Guid, все Guid передаются в big-endian. Дорабатывай существующие типы.
- MessageType содержит сообщения P2P, включая DISCOVER и PEER_INFO. HELLO, ERROR и PEER_LIST удалены; ErrorCode отсутствует. Возвращать серверные коды ошибок не нужно.
- ProtocolConstants содержит DefaultPort, размер чанка, лимит файла, параметры повторов, heartbeat и тайм-аут устройства. Смещение ackedSeq находится в PayloadsConstants. Добавляй остальные настройки по мере реализации.
- UdpTransport содержит единый цикл приёма, очередь входящих сообщений, seq, LossRate, поддержку broadcast и SendReliableAsync с проверкой ACK по deviceId, endpoint и seq. Ожидания ACK не забирают обычные сообщения из очереди. Конструктор транспорта по умолчанию выбирает свободный порт; при реализации приложения передавай DefaultPort явно. Дорабатывай существующий тип, не создавай параллельный транспорт.
- PeerService предоставляет обнаружение, доступность устройств и файловый обмен через FileExchange. `src/Protocol/Program.cs` — временный консольный клиент с командами peers, peer, offer, accept, reject, loss и quit. Пауза и возобновление ещё не реализованы полностью.
- `src/Client/Client.csproj` является Avalonia-клиентом и ссылается на Protocol. Сохраняй папки `Views/`, `ViewModels/`, `Models/` и `Assets/` внутри проекта.
- Namespace клиента сейчас различаются: `Client` у Program, App и ViewLocator, `ViewModels` у моделей представления, `local_file_share.Views` у MainWindow. Учитывай существующие объявления и ссылки в XAML; не переименовывай их вне текущего запроса.
- `tests/Protocol.Tests/Protocol.Tests.csproj` ссылается на Protocol и использует xUnit. `PacketTests` проверяет заголовок, CRC и отказ для старых кодов и превышения размера. `PayloadsTests` проверяет CHUNK, FILE_OFFER и ACK, включая фиксированные байты Guid. `UdpTransportTests` проверяет доставку, совпадение ACK, тайм-аут, отмену и повторы. Наличие этих тестов не означает полного покрытия требований.
- Клиент использует Avalonia 12.1.3 и CommunityToolkit.Mvvm 8.4.2. Целевые ОС: Windows, macOS, Linux.
- Сеть только через `System.Net.Sockets.Socket`, с `EnableBroadcast` для поиска устройств. UdpClient не использовать. Для CRC32 уже используется `System.IO.Hashing` 10.0.12.
- Не добавляй новые зависимости без необходимости. Не вводи DI-контейнеры, интерфейсы на будущее и лишние слои.
- До использования незнакомого API сверяйся с официальной документацией для установленной версии. Особенно проверяй Avalonia 12: drag & drop, StorageProvider и Clipboard. Не переноси API из Avalonia 11 наугад.
- Следуй локальным инструкциям RTK если файл доступен. Команды оболочки запускай через `rtk`; для неподдерживаемых команд используй `rtk proxy`.

## Требования, которые нужно сохранять при реализации

- Все приложения равноправны и обмениваются UDP-пакетами напрямую в одной локальной сети. Сервер, relay, регистрация и серверный реестр устройств отсутствуют.
- Каждое приложение при запуске создаёт deviceId Guid и сохраняет до закрытия. Первое поле каждого payload содержит deviceId отправителя, получатель задаётся endpoint назначения. peerId uint16 и assignedId больше не используются.
- Заголовок 12 байт: version 1 байт, type 1 байт, seq uint32, payloadLength uint16, crc32 uint32. Версия 1, числовые поля big-endian через BinaryPrimitives. Guid записывать и читать с явным big-endian представлением.
- CRC32 считается по заголовку с обнулённым полем CRC и payload. Максимальный payload 1060 байт, пакет 1072 байта. Неверную версию, CRC, тип, длину и некорректный payload молча отбрасывать без ACK.
- Каждый новый пакет получает новый seq, включая сообщения без ACK. Повторы одной reliable-отправки сохраняют seq. Счётчик общий для отправителя.
- Коды сообщений и форматы брать из таблицы SPEC.md. DISCOVER и PEER_INFO содержат deviceId и имя, HEARTBEAT содержит deviceId, ACK содержит deviceId и ackedSeq. HELLO, ERROR, SERVER_INFO и PEER_LIST отсутствуют.
- Имя кодируется длиной 1 байт и UTF-8 до 255 байт, пустое имя недопустимо. Проверять длины до чтения, некорректный UTF-8 и лишние байты отбрасывать. accepted и ok допускают только 0 и 1.
- По умолчанию приложение слушает UDP-порт 5000. Порт настраивается до запуска обмена. При занятом порте показывать ошибку, не обходить конфликт совместным использованием порта. Два экземпляра на одном компьютере используют разные порты, например 5000 и 5001.
- Пока обмен включён, раз в DiscoverInterval 2 с отправлять DISCOVER на 255.255.255.255:5000 и 127.0.0.1:5000. На запрос отвечать PEER_INFO в источник датаграммы. Собственное deviceId игнорировать. DISCOVER и PEER_INFO не требуют ACK.
- Список устройств строится локально по deviceId. DISCOVER и PEER_INFO добавляют устройство или обновляют имя и endpoint. Ручной ввод IP:порт нужен для нестандартного порта и блокировки broadcast; на вручную добавленные адреса также отправлять DISCOVER раз в 2 с.
- HEARTBEAT раз в 1 с отправлять известным устройствам онлайн и устройствам с передачами в паузе. Он требует ACK, но не повторяется. После 3 с без сообщений показывать отсутствие связи с устройством, после PeerTimeout 5 с убрать его из списка онлайн. Записи известных устройств остаются в памяти до закрытия приложения.
- Надёжная отправка ждёт ACK 200 мс, не более 5 отправок. Сверять deviceId, endpoint и ackedSeq. ACK сам не подтверждается. Исчерпание попыток CHUNK и FILE_DONE означает паузу, остальных reliable-сообщений ошибку, кроме FILE_OFFER для возобновления. Серверных ERROR нет, недоступность определяется тайм-аутами.
- Один цикл читает сокет и распределяет сообщения и ACK. Ожидание подтверждения не должно поглощать другие сообщения. На дубликат reliable-сообщения повторять ACK без повторного действия; CHUNK записывать по смещению index * 1024, для остальных использовать ограниченный набор deviceId и seq.
- Передача: FILE_OFFER, FILE_ANSWER, CHUNK по одному с stop-and-wait, FILE_DONE, FILE_RESULT. Чанк до 1024 байт, файл до 20 * 1024 * 1024 байт, текст UTF-8 до 1000 байт. ACK, решение пользователя и результат SHA-256 имеют разный смысл.
- Принимать файл в .part, хранить принятые чанки и nextIndex. Проверять индекс и длину относительно размера файла. Пустой файл имеет 0 чанков. Перед переименованием проверить все чанки и SHA-256; при неуспехе удалить .part и ответить FILE_RESULT с ok = 0.
- Очищать имя файла с учётом Windows и коллизий. Папка по умолчанию "Загрузки", при совпадении добавлять суффикс вроде (1).
- FILE_ANSWER содержит accepted и nextIndex. Для нового файла nextIndex равен 0, при отказе игнорируется. Ожидание FILE_ANSWER 60 с завершается ошибкой, ожидание FILE_RESULT 30 с паузой отправителя. Отсутствие чанков 10 с во время приёма означает паузу получателя, не действует во время решения пользователя и проверки SHA-256.
- В паузе сохранять .part, принятые чанки и nextIndex. Отправитель раз в ProbeInterval 2 с повторяет FILE_OFFER с тем же fileId и новым seq на текущий endpoint. Неудачный запрос сохраняет паузу и не сбрасывает PauseTimeout. Обнаружение вернувшегося deviceId обновляет endpoint без ручного переподключения.
- Возобновление определяется по deviceId отправителя и fileId. Метаданные должны совпадать. Получатель отвечает accepted = 1 и своим nextIndex без нового запроса пользователю. Неизвестный fileId считается новым предложением. nextIndex не превышает число чанков; если равен ему, отправлять FILE_DONE.
- Для сохранённого файла повторный FILE_OFFER получает accepted = 1 и nextIndex равный числу чанков, повторный FILE_DONE получает ACK и прежний FILE_RESULT. Для завершённой проверки с ok = 0 повторное предложение отклоняется. Результаты хранить по deviceId отправителя и fileId до закрытия приложения.
- PauseTimeout 120 с каждая сторона отсчитывает от своего входа в паузу. По истечении ошибка и удаление .part у получателя. Отмена в паузе локальная, без сетевого сообщения отмены, вторая сторона завершает по своему тайм-ауту.
- LossRate от 0 до 100% действует на приём и отправку, включая поиск и ACK. Временный консольный клиент поддерживает --loss N и loss N, UI содержит поле и переключатель обрыва связи с восстановлением прежнего значения.
- Общие настройки собирать в ProtocolConstants по мере реализации. Размеры и смещения использовать из PacketOffsets, PayloadsConstants и Packet, не дублировать.
- UI содержит имя и локальный порт, переключатель обмена, список устройств с адресами и доступностью, ручной адрес, выбор файла и drag & drop, принятие или отклонение файла, отправку текста, список передач и копирование принятого текста. В паузе сохранять прогресс и показывать оставшееся время и отмену. При отключении обмена передачи переходят в паузу, её таймер продолжает действовать.
- Панель подробностей показывает отправки, подтверждения, повторы, потери, паузы и возобновления. Сетка чанков необязательна.
- Вне объёма: TCP поверх UDP, скользящее окно, шифрование и аутентификация, NAT traversal, интернет, мобильные ОС, папки, обнаружение за пределами подсети и возобновление после перезапуска приложения. deviceId не является доказательством подлинности устройства.

## Правила реализации полного обмена

Эти правила применяются, когда автор просит реализовать полный обмен. Они не разрешают расширять отдельный запрос на весь проект. Форматы, численные ограничения и поведение при тайм-аутах брать из SPEC.md.

- Общую логику обнаружения, доступности устройств, файловых передач и текста размещать в `src/Protocol/`. Она не должна зависеть от Console, Avalonia, ViewModel или системного буфера обмена. Консоль и будущий Client должны использовать одну реализацию обмена.
- UdpTransport отвечает за сокет, сериализацию, seq, потери, маршрутизацию ACK и reliable-отправку. Решение пользователя, файлы, список устройств и состояния передач реализовывать отдельно от транспорта. Добавлять обычные классы по мере необходимости, без DI-контейнера и интерфейсов на будущее.
- Program.cs отвечает за аргументы, команды и вывод временного клиента. При расширении демо переносить общую логику из Program.cs в Protocol. Не реализовывать передачу повторно при переходе к Avalonia.
- Предоставить вызывающему коду операции запуска и отключения обмена, ручного добавления адреса, отправки файла и текста, принятия или отклонения предложения и отмены передачи в паузе. Изменения устройств, предложений, прогресса, состояний и полученного текста должны быть доступны консоли и Client. Конкретные сигнатуры выбирать после изучения существующего кода.
- У общего обработчика должен быть один потребитель ReceiveAsync. Ожидание решения пользователя, FILE_ANSWER, FILE_RESULT, ACK и проверка SHA-256 не должны останавливать обработку других сообщений. Определить, кто изменяет общее состояние; не допускать гонок таймеров, входящих пакетов и действий пользователя.
- ACK отправлять после проверки payload и условий обработки сообщения. Дубликат подтверждать повторно без повторного действия. Использовать существующий ProcessedMessages для ограниченного набора deviceId и seq; отдельно сохранять состояние чанков и завершённых передач по правилам SPEC.md.
- Различать подтверждение сообщения, решение принять файл и результат проверки SHA-256. Успешная reliable-отправка FILE_OFFER не означает принятие файла, ACK на FILE_DONE не означает успешное сохранение.
- Сначала реализовать обнаружение, ручные адреса и доступность устройств. Затем полный сценарий файла, паузу и возобновление, CLIPBOARD. После проверки общего обмена подключать Avalonia. Статистику добавлять в местах отправки, подтверждения, повторов, потерь и смены состояния, чтобы UI мог её показывать.
- Для файлов соблюдать проверку метаданных, индексов и длины чанков, запись в .part и проверку SHA-256 перед переименованием. Не перезаписывать существующие файлы. Учитывать Windows при очистке имени, даже при запуске на macOS или Linux.
- Пауза сохраняет прогресс. Пробный FILE_OFFER не сбрасывает PauseTimeout; endpoint брать из актуальной записи устройства. Повторное предложение завершённого файла и повторный FILE_DONE обрабатывать по сохранённому результату, без повторного запроса пользователю и создания нового файла.
- Отключение обмена останавливает сетевые операции и переводит незавершённые передачи в паузу. Отсчёт PauseTimeout продолжается. При закрытии освобождать сокет и файловые ресурсы, завершать фоновые задачи и ожидания; возобновление после перезапуска не реализовывать.
- Временный клиент должен позволять проверить обнаружение, отправку и принятие или отказ от файла, текст и loss. Поддержать `--loss N` и команду `loss N` по SPEC.md. Ошибки показывать пользователю, неожиданные исключения не скрывать.
- Добавлять небольшой набор тестов на поведение: полный обмен и совпадение SHA-256, отказ, дубликаты, некорректный чанк, возобновление и очистку .part после тайм-аута. Существующие тесты кодеков и транспорта сохранять; не дублировать их для каждой новой функции.
- Готовность объявлять по выполненным сценариям, а не по наличию классов или успешной сборке. Отдельно указывать, что проверено автоматически, двумя локальными процессами и на разных ОС в LAN.

## Порядок и проверка

Выполняй только запрошенный шаг из SPEC.md: Protocol для P2P, прямой обмен через временный консольный клиент, пауза и возобновление, CLIPBOARD, Avalonia UI, статистика и документация. Временный клиент добавлять только на этапе проверки обмена.

- После запрошенного изменения проверяй сборку через `rtk proxy dotnet build LocalFileShare.slnx`. Не скрывай ошибки и не подавляй предупреждения вместо исправления причины.
- После изменения логики Protocol запускай `rtk proxy dotnet test tests/Protocol.Tests/Protocol.Tests.csproj`. Дополняй существующие тесты поведением в пределах запроса, включая согласованный сетевой формат P2P.
- Текущая команда клиента: `rtk proxy dotnet run --project src/Client/Client.csproj`. Server больше не является частью целевого сценария. Пока нужные функции не реализованы, не объявляй их доступными через эту команду.
