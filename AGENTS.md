# Инструкции для нейросети

## Как помогать

Это учебная семестровая работа по сетевому программированию. Автор хочет написать реализацию сам. Полное ТЗ находится в [SPEC.md](SPEC.md).

- Выполняй только конкретно запрошенный шаг. Наличие полного ТЗ не разрешает реализовать весь проект.
- По умолчанию объясняй подход, предлагай следующий небольшой шаг и помогай разобраться с ошибками. Пиши готовую реализацию только по запросу автора.
- Если просят структуру, ограничься проектами, ссылками между ними и кратким описанием ответственности. Не добавляй заранее сервисы, интерфейсы, заглушки методов и готовую бизнес-логику.
- Документацию, Markdown-файлы и итоговые отчёты пиши на русском. Код, обычные комментарии и тексты коммитов пиши на английском. Интерфейс и сообщения приложения пиши на русском.
- Для сложных методов пиши XML-summary на русском с назначением и смыслом входных параметров. Не добавляй комментарии, пересказывающие код; сохраняй объяснения ограничений и причин решений.
- Перед изменениями изучай существующий код и используй принятые в проекте подходы.
- Перед архитектурным изменением коротко объясняй его пользу и компромисс.
- Не переписывай самостоятельную работу автора без необходимости для текущего запроса.
- Требования бери из [SPEC.md](SPEC.md), сетевые форматы и тайм-ауты из [PROTOCOL.md](PROTOCOL.md). Не дополняй неоднозначные правила без обсуждения с автором.

## Конвенции кода

- Форматирование C# — CSharpier; кодировка, отступы и окончания строк — из `.editorconfig`.
- Пустыми строками отделяй логические группы полей и этапы методов: проверки, подготовку ресурсов, выполнение операции, обновление состояния и уведомления. Связанные присваивания и подписки оставляй вместе.
- Типы и методы — PascalCase, параметры и локальные переменные — camelCase, закрытые поля — `_camelCase`, константы — PascalCase. Пространства имён — файловые.
- У условий и циклов всегда ставить фигурные скобки. `var` использовать, когда тип очевиден или его имя не помогает чтению; для простых числовых и строковых значений указывать тип.
- Для стандартных проверок использовать `ArgumentNullException.ThrowIfNull`, `ArgumentException.ThrowIfNullOrEmpty` / `ThrowIfNullOrWhiteSpace`, методы `ArgumentOutOfRangeException.ThrowIf*` и `ObjectDisposedException.ThrowIf(condition, this)`. Если подходящего метода нет, использовать явный `if` и `throw` с `nameof` параметра и английским сообщением. Неверное состояние — `InvalidOperationException`. Не создавать обёртки над `ThrowIf*`, если они не выполняют дополнительную работу, например синхронизацию.
- Отмена — через `CancellationToken.ThrowIfCancellationRequested()`. Ожидаемую отмену перехватывать с проверкой токена. Сохранять исходное исключение через `throw;`, не скрывать неожиданные ошибки.
- Ресурсы освобождать через `using` / `await using`, захват `SemaphoreSlim` — через `try/finally`. Короткое синхронное изменение состояния защищать `lock`; не заменять все блокировки семафорами.
- Папки группировать по задаче (`Peers`, `Transfers`, `Transport`), интерфейс хранить рядом с реализацией. Добавлять интерфейс только для используемого контракта или подмены в тестах.
- README.md содержит только структуру проекта.

## Работа с существующим кодом

Стек указан в SPEC.md, структура проектов в [README.md](README.md).

- `src/Protocol/` является классовой библиотекой без точки входа и не зависит от Console, Avalonia, ViewModel и буфера обмена. Клиент и тесты используют общую реализацию обмена.
- Дорабатывай существующие типы: `UdpTransport` отвечает за сокет, seq, потери и ACK; `PeerService` за обнаружение и маршрутизацию; `ExchangeService` за управление обменом и текст; `FileExchange` за файловый сценарий. Не создавай параллельный транспорт или отдельную реализацию передачи для UI.
- Источником состояния включения обмена и сетевых токенов является `ExchangeService`. `FileExchange` получает токен сессии и владеет только отменой собственного закрытия.
- `OutgoingFileExchange` отвечает за предложение файла, отправку чанков и возобновление исходящих передач. `FileBackgroundTaskHandler` учитывает операции и фоновые ответы, исключает одновременные дубли ответов и ожидает завершения задач при закрытии.
- `FileExchange` разбирает payload файловых сообщений; `FileTransferService` получает разобранные параметры и владеет состоянием передач и его блокировкой. Для пользовательских сообщений используй `FileTransfer.ErrorCode`; `Error` содержит техническое описание для диагностики.
- Для операций над существующей передачей используй `TransferKey`; в payload передавай отдельные `deviceId` отправителя и `fileId`. Снимки `FileTransfer` доступны внешнему коду только для чтения свойств.
- Используй `ProtocolConstants`, `PacketOffsets` и `PayloadsConstants` для настроек, размеров и смещений. Для дедупликации сообщений используй `ProcessedMessages`, для чанков и результатов существующее состояние передач.
- Сетевой формат находится в `Messages/`, файловые операции в `Transfers/Files/`, модели передач в `Transfers/Models/`. Остальные предметные папки и их назначение указаны в README.md; тесты Protocol находятся в `tests/Protocol.Tests/`.
- В `Extensions/` размещай операции без собственного состояния, используемые несколькими частями протокола. Состояние передач, блокировки и управление временем жизни оставляй у их владельцев.
- Сохраняй единый потребитель `ReceiveAsync`. Согласовывай изменения состояния из таймеров, входящих сообщений и действий пользователя. Завершай фоновые задачи при закрытии.
- Avalonia использует общий обмен Protocol. Переноси сетевые уведомления в поток UI; не дублируй сетевые сценарии в клиенте.
- В библиотеке Protocol пространства имён должны соответствовать папкам: `Protocol`, `Protocol.Transport`, `Protocol.Transfers.Models` и т. д. В Client используй `Client`, `Client.Views` и `Client.ViewModels` с соответствующими ссылками в XAML.
- Не добавляй зависимости, DI-контейнеры, интерфейсы и слои на будущее. Перед незнакомым API проверяй официальную документацию установленной версии, особенно Avalonia 12: drag & drop, StorageProvider и Clipboard.

## Проверка изменений

- Проверяй сборку: `rtk proxy dotnet build LocalFileShare.slnx`. Исправляй причины ошибок и предупреждений, не подавляй их.
- Тесты нужны только для Protocol. Не создавай тесты Client, ViewModel, UI и клиентских настроек.
- После изменения логики Protocol запускай `rtk proxy dotnet test tests/Protocol.Tests/Protocol.Tests.csproj`. Поддерживай небольшой набор понятных проверок основных сценариев: передача и SHA-256, отказ, текст, потери, пауза, возобновление и очистка временных файлов. Избегай сложных тестов внутренних методов и редких комбинаций состояний без отдельного запроса автора.
- Сценарии приёмки и команды запуска находятся в SPEC.md. Готовность оценивай по выполненным сценариям; отдельно указывай автоматические тесты, два локальных процесса и разные ОС в LAN.
- В отчёте кратко опиши результат, команды запуска и непроверенные сценарии.
