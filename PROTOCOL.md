# Спецификация протокола

## Общие правила

- Транспорт: **UDP**, прямой обмен в LAN, порт по умолчанию **5000**.
- Порядок байт: **big-endian**, включая 16 байт `Guid`.
- Типы: `u8`, `u16`, `u32`, `u64` — беззнаковые целые; `guid` — 16 байт.
- Версия: **1**. Максимум: **1060 байт payload**, **1072 байта пакет**.
- Поля следуют в указанном порядке без выравнивания.
- Первый элемент каждого payload — `D`: `deviceId` отправителя, созданный на время работы приложения. Получатель задаётся адресом назначения.
- `NAME` — длина `u8` и от 1 до 255 байт строгого UTF-8. Лишние байты, пустое имя и некорректный UTF-8 запрещены.

## Заголовок — 12 байт

| Смещение | Размер | Поле | Описание |
|---------:|-------:|------|----------|
| 0 | 1 | `VERSION` | `u8`, значение 1 |
| 1 | 1 | `TYPE` | `u8`, код сообщения |
| 2 | 4 | `SEQ` | `u32`, общий счётчик отправителя, с переполнением в 0 |
| 6 | 2 | `PAYLOAD_LENGTH` | `u16`, 0–1060 |
| 8 | 4 | `CRC32` | CRC32 заголовка с обнулённым полем CRC и payload |

Каждый новый пакет, включая ACK, получает новый `SEQ`. Повторы одной надёжной отправки сохраняют `SEQ`. Неверные версия, тип, CRC, длина или payload молча отбрасываются без ACK.

## Сообщения

| Код | Имя | Направление | ACK | Payload |
|-----|-----|-------------|-----|---------|
| `0x02` | `HEARTBEAT` | устройство → известное устройство | да¹ | `D guid` |
| `0x03` | `ACK` | получатель → отправитель | нет | `D guid, ACKED_SEQ u32` |
| `0x05` | `DISCOVER` | устройство → broadcast / заданный адрес | нет | `D guid, NAME` |
| `0x06` | `PEER_INFO` | устройство → источник DISCOVER | нет | `D guid, NAME` |
| `0x20` | `FILE_OFFER` | отправитель → получатель | да | `D guid, FILE_ID guid, SIZE u64, SHA256 byte[32], NAME` |
| `0x21` | `FILE_ANSWER` | получатель → отправитель | да | `D guid, FILE_ID guid, ACCEPTED u8, NEXT_INDEX u32` |
| `0x30` | `CHUNK` | отправитель → получатель | да | `D guid, FILE_ID guid, INDEX u32, DATA byte[0..1024]` |
| `0x31` | `FILE_DONE` | отправитель → получатель | да | `D guid, FILE_ID guid` |
| `0x32` | `FILE_RESULT` | получатель → отправитель | да | `D guid, FILE_ID guid, OK u8` |
| `0x40` | `CLIPBOARD` | отправитель → получатель | да | `D guid, TEXT` — до 1000 байт UTF-8 |

¹ HEARTBEAT ждёт ACK, но не повторяется.

- `ACCEPTED` и `OK`: только **0** или **1**. `NEXT_INDEX` — первый недостающий чанк; для нового файла 0, при отказе игнорируется, не превышает число чанков.
- `SIZE` — до **20 × 1024 × 1024 байт**. Смещение чанка — `INDEX × 1024`; длина точно соответствует оставшимся данным, максимум 1024. У пустого файла 0 чанков.
- `TEXT` занимает остаток payload, без отдельного поля длины. `SHA256` — хеш всего файла.
- `HELLO`, `ERROR`, `SERVER_INFO`, `PEER_LIST` отсутствуют; коды `0x01`, `0x04`, `0x10` не используются. `deviceId` не является аутентификацией.

## Поиск устройств

- Каждые **2 с** отправлять DISCOVER на `255.255.255.255:5000`, `127.0.0.1:5000` и ручные адреса. Отвечать PEER_INFO в источник датаграммы, своё `deviceId` игнорировать.
- DISCOVER и PEER_INFO добавляют устройство или обновляют имя и адрес по `deviceId`. Ручные адреса и известные устройства хранятся до закрытия приложения.
- HEARTBEAT каждые **1 с** отправлять устройствам онлайн и устройствам с передачами в паузе. Только корректные сообщения ожидаемого устройства обновляют доступность.
- Через **3 с** без сообщений — отсутствие связи; через **5 с** — убрать из списка онлайн, сохранив известную запись. Повторное обнаружение обновляет адрес без ручного подключения.
- Порт настраивается до запуска; занятый порт — ошибка без совместного использования. Два локальных экземпляра используют, например, 5000 и 5001. Broadcast ограничен подсетью; прямой входящий UDP должен быть доступен на каждом устройстве.

## Подтверждения и передача

- Надёжная отправка: ожидание ACK **200 мс**, максимум **5 отправок**. Сверять `deviceId`, адрес источника и `ACKED_SEQ`. ACK не подтверждается.
- Подтверждать после проверки payload и условий обработки. Дубликат подтверждать повторно без повторного действия. Для CHUNK хранить принятые индексы, для остальных — ограниченный набор пар `deviceId, seq`.
- Последовательность: `FILE_OFFER → FILE_ANSWER → CHUNK… → FILE_DONE → FILE_RESULT`. Чанки отправляются по одному, следующий — после ACK предыдущего.
- ACK означает обработку сообщения, FILE_ANSWER — решение пользователя, FILE_RESULT — результат проверки и сохранения. Ожидания и SHA-256 не блокируют общий приём.
- Данные писать в `.part`. Перед переименованием проверить все чанки и SHA-256; успех — `OK = 1`, иначе удалить `.part` и отправить `OK = 0`. Очищать имя по правилам Windows, избегать перезаписи суффиксом ` (1)`.

## Тайм-ауты

| Условие | Время | Результат |
|---------|------:|-----------|
| Нет ACK для CHUNK или FILE_DONE | 5 отправок | Пауза |
| Нет ACK для другого надёжного сообщения | 5 отправок | Ошибка; пробный FILE_OFFER сохраняет паузу |
| Нет FILE_ANSWER | 60 с | Ошибка |
| Нет FILE_RESULT | 30 с | Пауза отправителя |
| Нет чанков при приёме | 10 с | Пауза получателя; не действует при решении пользователя и проверке SHA-256 |
| Пробный FILE_OFFER в паузе | Каждые 2 с | Запрос возобновления |
| Пауза без успешного возобновления | 120 с | Ошибка, получатель удаляет `.part` |

## Возобновление

- Ключ передачи — `deviceId` отправителя и `fileId`. Пауза сохраняет данные, принятые чанки и `nextIndex`.
- Отправитель повторяет FILE_OFFER с тем же `fileId`, новым `seq` и актуальным адресом. Неудачный запрос не сбрасывает таймер паузы и не останавливает поиск устройства.
- При совпадении имени, размера и SHA-256 получатель отвечает `ACCEPTED = 1` и своим `NEXT_INDEX` без повторного вопроса. Изменённые метаданные отклоняет; неизвестный `fileId` — новое предложение.
- Отправитель принимает индекс получателя; если он равен числу чанков, сразу отправляет FILE_DONE.
- Для сохранённого файла повторный FILE_OFFER получает принятие и индекс после последнего чанка; повторный FILE_DONE — ACK и прежний FILE_RESULT. После `OK = 0` повторный FILE_OFFER отклоняется. Результаты сохраняются до закрытия приложения.
- Каждая сторона отсчитывает 120 с от своего входа в паузу. Локальная отмена удаляет `.part`, сообщения отмены нет; вторая сторона завершает ожидание по своему тайм-ауту.
- Отключение обмена переводит незавершённые передачи в паузу; её таймер продолжает действовать. Перезапуск приложения не сохраняет возможность возобновления.
